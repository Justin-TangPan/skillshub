# 评估报告模板

## 分值与等级

| 指标 | 满分 |
|---|---:|
| 场景需求明确度 | 15 |
| 客户痛点强度 | 10 |
| SAC 显著降低部署门槛 | 15 |
| 云服务组合度 | 10 |
| 云资源消费潜力 | 5 |
| 可标准化复制 | 15 |
| 开源项目成熟度 | 10 |
| Demo 与可展示性 | 5 |
| 一线/伙伴易理解性 | 5 |
| 开发者吸引力 | 5 |
| 与现有方案差异化 | 5 |
| **总计** | **100** |

每项给出得分和一句证据化理由。等级：

- 80–100：核心解决方案实践；优先 PoC 与 SAC 立项。
- 65–79：普通解决方案实践；控制投入，先验证场景和部署链路。
- 50–64：Developer Practice、最佳实践、博客或轻量 Demo。
- 0–49：暂不建议立项。

若明确缺少客户场景、SAC 增量或可复制性，或 License/维护存在重大风险，即使总分较高也下调等级并解释原因。

## 报告结构

# 项目结论

- 项目名称：
- 解决方案实践适配度：
- 总分：XX / 100
- 建议分类：核心解决方案实践 / 普通解决方案实践 / Developer Practice / 暂不建议立项
- 证据置信度：高 / 中 / 低
- 一句话结论：

# 1. 项目是什么

用非技术人员能理解的语言说明核心能力、主要用户、典型使用方式和技术架构简述。

# 2. 客户场景

先给出场景句，再列真实场景：

| 场景 | 目标客户 | 客户问题 | 项目能力 | 业务价值 |
|---|---|---|---|---|

# 3. SAC Value Gap

分别以流程链展示“客户自行部署”和“解决方案实践部署”，然后明确 SAC 减少的工作、失败点和运维成本。直接判断增量是否足以支撑产品化投入。

# 4. 云服务组合

分别给出 MVP 与企业级架构，解释每项云服务为何必要，并判断是拓客入口型还是资源消费型。不要强行堆叠云产品。

# 5. 商业价值 vs 开发者价值

分别判断商业市场价值和开发者价值，并放入二维矩阵：

| | 开发者价值低 | 开发者价值高 |
|---|---|---|
| 商业价值高 | 企业解决方案 | 核心解决方案实践 |
| 商业价值低 | 低优先级 | Developer Practice |

# 6. 可复制性

说明可固定部分、需参数化部分、客户定制部分、能否形成模板，并给出 A/B/C/D 分类。

# 7. 风险

至少核查 License、停止维护、技术稳定性、云服务替换、数据安全、依赖组件、企业级能力不足、与现有方案重复。说明风险证据、影响和可行缓解措施；未知项标注待验证。

# 8. 评分表

列出全部 11 项的“得分 / 满分”和一句理由，并校验合计为 100 分制。

# 9. 最终立项建议

先明确回答三个问题：客户为何需要、方案实践的增量价值、能否近乎同构复制给下一个客户。

若建议立项，继续给出：

- 第一版 SAC MVP 的最小组件和自动化范围
- 第一期明确不做的内容
- 进入 PoC/立项前必须验证的事项
- 建议方案名称
- 建议副标题
- 一句话价值主张：“帮助【客户】快速完成【目标】，无需【传统复杂过程】。”
- 30 秒销售话术：普通售前或伙伴可复述，避免技术术语堆砌

若不建议立项，指出更低成本的替代交付形式及重新评估的触发条件。

末尾列出关键来源与核查日期；不要把来源链接集中起来代替正文中的证据引用。
