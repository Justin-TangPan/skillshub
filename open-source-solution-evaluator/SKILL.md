# 开源解决方案实践评估

目标不是判断项目“好不好”，而是判断它能否被包装成低门槛、可部署、可复制、可传播并能带动合理云服务消费的解决方案。

## 研究证据

用户提供 GitHub URL 或公开项目名称时，先检索最新的一手资料。至少核查：README、部署与架构文档、Release、License、提交和贡献者活跃度、Issues，以及 Docker、Compose、Helm/Kubernetes、API 支持。优先项目仓库、官方文档和许可证原文；标明核查日期，并为会变化的事实附链接。

区分事实、推断与未知。资料不足时继续用现有证据完成评估，但明确降低置信度，不把缺失信息当作正面证据。Star 仅作成熟度旁证，不能替代客户价值判断。

## 判断顺序

1. 先形成场景句：“面向【目标客户】，解决【业务问题】，通过【项目核心能力】，实现【业务价值】。”无法形成可信场景时，降低推荐等级。
2. 比较客户自行部署与 SAC/解决方案实践部署的完整链路，找出被消除的安装、配置、集成、网络、安全、版本兼容和排错工作。如果原项目已能在约 5 分钟内可靠部署，要求存在其他明确增量价值，否则不建议重投入。
3. 识别项目天然需要的最小云资源组合。不要因为服务可用就强行加入；区分拓客入口型和资源消费型，并区分 MVP 与企业级架构。
4. 判断 80% 架构与流程能否固定、客户差异能否参数化，以及是否必须改源码或一客一议。归类为 A 高度标准化、B 可标准化但需适配、C 项目制明显、D 不适合标准方案。
5. 分别评估商业市场价值和开发者价值，再定位为核心解决方案实践、企业解决方案、Developer Practice 或低优先级。
6. 审视成熟度、传播性与风险，最后评分。分数是辅助；场景、SAC 增量、可复制性、License/维护状态任一核心项明显失败时，主动下调推荐等级。

至少提出 3 个有证据或合理业务逻辑支持的客户场景；不足 3 个时如实给出，不得凑数。架构用简洁文本树表达即可。

## 必答问题

结论必须直接回答：

- 客户为什么需要它？用业务需求回答，不复述功能。
- 做成解决方案实践后，比客户自己部署强在哪里？指出可验证的增量价值。
- 它能否以几乎相同的方式复制给下一个客户？说明固定项、参数项和定制项。

## 输出

执行评估时必须读取并遵循 [references/report-template.md](references/report-template.md)。保持批判性：不因热门、先进或可运行在 ECS 上而高估价值；对推测明确标注。
