# 华为云解决方案资产结构化管理

同时处理现网方案清单和单条资产元数据。不得把现网页面中没有的信息描述为官网事实。

## 现网清单与表格

标准工作簿为技能目录下的 `解决方案实践.xlsx`，字段顺序为：

`序号、主标签、一级场景、二级场景、解决方案名称、方案名或实践名（英文）、ID编码、方案站点、中国站区域、国际站区域、中国站链接、国际站链接、简述`

需要创建、刷新或补充清单时，运行：

```bash
python scripts/sync_solution_practices.py [工作簿路径]
```

脚本读取中国站和国际站的解决方案实践页。页面源码中的卡片数组需反转后才是官网展示顺序。一个工作表只能有一套行序，因此以中国站目录为主序；仅国际站方案按国际站顺序插在下一个共有方案之前。若前后共有方案在中国站的顺序相反，无法同时满足两站相邻顺序，保留下一个共有方案作为锚点并在审计输出中报告冲突；若没有后续共有方案，则接在前一个共有方案之后。不得声称合并后的行序同时等于两站顺序。

链接仅接受 HTTPS 的 `www.huaweicloud.com` `.html` 详情页。目录中出现格式异常链接时停止同步并报告，不把它当成有效站点链接。生成的`方案站点`必须由有效的中国站、国际站链接推导，不依据手填标签或另一站链接猜测。需要核验链接能否访问时运行 `python scripts/sync_solution_practices.py [工作簿路径] --check-links`；它会在写入前检查目录与工作簿链接，任一链接失败则报告并停止。

工作簿不存在时创建；存在时按链接 ID 和规范化标题匹配，按表头名写入以兼容列顺序调整，并保留已有样式、列宽和冻结窗格。目录新增的方案会按主序加入；官网目录未列出的既有行保留并报告，不自动删除。同步后查看审计输出：核对每站官网条数、未匹配方案、站点顺序冲突、新增方案、保留的旧行、无效链接和缺少区域的站点。官网卡片没有的英文名称、二级场景和区域不得猜填。

区域必须逐站核实。根据该站方案详情页的部署页、模板 URL 或明确的支持区域信息填写；中国站和国际站分别记录，不从站点标签、另一站区域或相似方案推断。无法从现网证据确认时留空并报告。

同步后检查新增行。脚本只能可靠填写官网公开字段；新增行的英文名称、二级场景和区域需按本技能其余规则补齐后再交付。官网名称违反下述命名规则时，不擅自改写官网现名；只有工作簿保留`备注`列时才在该列说明。

用户要求把一个新方案加入工作簿时，先生成完整七字段元数据，再通过 `--record-json` 写入；JSON 使用表头字段名，例如：

```bash
python scripts/sync_solution_practices.py 解决方案实践.xlsx --record-json '{"解决方案名称":"示例名称","方案名或实践名（英文）":"Example Name","ID编码":"example-name","一级场景":"AI","二级场景":"Agent与知识应用","主标签":"应用方案","中国站区域":"","国际站区域":"","中国站链接":"","国际站链接":"","简述":"示例简介","方案站点":""}'
```

未发布资产的两个站点链接、区域和`方案站点`留空。已发布资产必须以现网结果为准。不要仅因名称相似覆盖另一条资产；有歧义时保留为新行。

只要求单条命名而未要求维护表格时，不修改工作簿，按文末七字段格式回答。

## 命名前确认信息

生成元数据前，如信息不足，先向用户确认以下四点，不凭空假设：

1. 方案类型：是应用方案、最佳实践还是 Skills。
2. 主要做了什么：交付物或能力解决什么具体问题、如何解决。
3. 核心场景价值：面向谁、带来什么价值、最适合归入哪些业务场景（可为一个或多个）。
4. 是否纳入资产库：生成结果后，询问是否写入 `解决方案实践.xlsx` 资产库；得到确认后再用 `--record-json` 写入，未确认前不改动工作簿。

## 资产类型与命名

先判断命名类型，再选主标签；两者是不同维度，不因交付物叫“最佳实践”就默认使用“基于 XXX 构建 XXX”。按以下顺序判断，A 类优先于 B 类：

| 类型 | 判断依据 | 首选名称 |
|---|---|---|
| A 热点项目 / 开源项目 / 明确品牌项目 | 项目名已有认知、社区活跃、近期受关注，或自身有明确品牌；用户首先想知道项目是什么 | `项目名 + 核心品类` |
| B 部署交付型 | 用户主要获取部署流程或交付能力，项目品牌认知弱，重点是建成环境或平台 | `快速搭建/快速部署 + 对象及品类`；只有确有一键能力才用`一键部署` |
| C 业务场景型 | 用户首先按业务问题寻找方案，项目品牌不是主要入口 | 简洁的业务场景或成果名称 |
| D 平台能力型 | 交付物确为具备相应范围的平台，核心卖点是平台能力 | `平台名 + 核心能力品类`，无品牌时用简洁的能力名称 |

命名优先回答“这是什么项目/产品”和“属于什么核心能力品类”。A 类默认保留官方项目名，后接最容易理解、与实际能力相符的市场品类词，如`开源编程 Agent`、`智能体开发平台`、`AI 决策模型`、`AI 编程工具`、`模型推理服务`、`RAG 知识库平台`、`AI 工作流平台`。只有项目实际开源时才写“开源”。不要因方案包含部署步骤，就把 A 类改成“快速搭建 XX”“一键部署 XX”或“基于 XX 构建 XX”。

热点概念可用于传播，但须核实项目与概念的关系。项目有正式名称和热点传播点时，正式名称保持准确、稳定；相关热点词放入副标题、简介或标签，不用可能冒充另一项目的词替换项目名。例如正式名称`Laya 开源 AI 决策模型`，副标题可写“轻量部署 System One 模型，快速体验 Jev 类低时延结构化决策能力”；不得命名为`Jev 开源模型`。副标题仅在任务要求或资产载体支持时提供，不改变文末七字段输出格式。

候选名称应适合官网卡片、导航、搜索与分享。结合当前市场认知、用户最易理解的能力、热点传播价值和事实准确性选择，不机械套模板。尽量控制在 6–16 个汉字左右（英文项目名按实际显示长度判断），上限 20 个字；避免长句。名称由项目名与定位组成时，中英文均使用单个空格分隔，不使用逗号、冒号或破折号。轻量级方案少用`企业级平台`、`一体化解决方案`、`全栈平台`、`综合管理平台`、`智能中台`，除非能力范围确实支持。

示例与反例：

| 情况 | 推荐 | 避免 | 原因 |
|---|---|---|---|
| A 类热门开源项目 | `OpenCode 开源编程 Agent` | `快速搭建 OpenCode 编程环境` | 项目名和品类是主要识别信息 |
| A 类热点项目 | `Laya 开源 AI 决策模型` | `Jev 开源模型` | 热点关联不能替代真实项目身份 |
| A 类明确品牌 | `Dify 智能体开发平台` | `基于 Dify 构建智能体开发平台` | 品牌与能力已足够清楚 |
| B 类部署交付 | `快速搭建 Dify 智能体平台`、`快速部署开源大模型推理服务` | 为弱品牌对象硬套项目名 | 用户主要需要部署成果 |
| C 类业务场景 | `智能问数与数据分析` | `企业级一体化智能数据中台` | 直接表达用户任务，避免夸大 |
| D 类平台能力 | `RAG 知识库平台` | `全栈 AI 综合管理平台` | 只写实际具备的核心能力 |

主标签只能选择一个：

- `应用方案`：交付物是可部署、运行或使用的应用或软件；按上述 A–D 判断命名，项目有认知时优先保留项目名。
- `最佳实践`：交付物是可按步骤完成的场景实践，包含架构、方法、配置或操作步骤；A 类仍优先`项目名 + 核心品类`，B 类可用部署动作，C 类可用场景名。仅当技术路径本身是用户要找的内容时，使用`基于 XXX 构建/实现 XXX`。
- `Skills`：交付物是一个或多个 Skill 形成、可在 OfficeAce、码道或 AgentArts 中长期使用的能力。标题直接表达业务能力，默认不出现 OfficeAce、码道、AgentArts、Skill、Skills，也不使用"XX助手""XX专家""XX Agent""XX神器"；这里的`XX Agent`限制只针对 Skills 标题，不限制 A 类开源项目的真实品类如`编程 Agent`。

## Skills 聚合页模型

SAC 展示页面与后台 Skill 是两个粒度：

- 一级场景是稳定的用户业务领域，例如`智能运维`。
- 二级场景是用户要完成的任务，也是一个独立 Skills 详情页，例如`根因分析`、`异常检测`、`资源监控`、`故障处置`。
- 详情页内按产品设置 Tab，例如`LTS`、`CCE`、`RDS`、`ECS`；每个 Tab 对应一个可独立安装、升级、授权和统计的后台 Skill。
- 后台 Skill ID 使用`产品-能力`，例如`lts-root-cause-analysis`、`cce-root-cause-analysis`、`rds-root-cause-analysis`。不要把多个产品实现合并成一个后台 Skill。

用户应先按任务找到二级场景，再选择产品实现；不要按云服务为每个同类 Skill 重复创建 SAC 页面。只有当某个实现的目标用户、输入输出、执行流程或核心价值明显不同时，才拆成新的二级场景页。

智能运维 Skills 优先使用以下层级：

| 一级场景 | 二级场景 | Tab 示例 |
|---|---|---|
| `智能运维` | `根因分析` | LTS、CCE、RDS、ECS |
| `智能运维` | `异常检测` | LTS、CCE、RDS |
| `智能运维` | `资源监控` | ECS、CCE、RDS |
| `智能运维` | `故障处置` | CCE、ECS、RDS |

这里的 Tab 示例不是封闭枚举；新增产品实现时追加 Tab，不另建页面。

## 场景分类

以用户最终解决的问题为准，不因使用 AI、Agent 或 Skill 就默认归类为 AI。Skills 聚合页优先使用上一节定义的业务领域与能力任务；应用方案和最佳实践使用以下有效组合：

| 一级场景 | 二级场景 |
|---|---|
| `AI` | `Agent与知识应用` |
| `AI` | `大模型与AI平台` |
| `数据分析与管理` | `数据平台与计算` |
| `数据分析与管理` | `智能问数与数据Agent` |
| `应用现代化` | `云原生与DevOps` |
| `应用现代化` | `应用与服务器` |
| `应用现代化` | `应用与内容加速` |
| `应用现代化` | `行业应用与HPC` |
| `网络` | `网络连接与公网` |
| `安全与合规` | `安全防护` |
| `安全与合规` | `安全合规` |
| `云迁移` | `数据迁移与容灾` |
| `运维监控` | `监控、日志与运维工具` |

例如，自然语言查询 DWS 数据归为`数据分析与管理 / 智能问数与数据Agent`；通过 Skill 巡检云资源归为`运维监控 / 监控、日志与运维工具`。

一个方案可同时归入多个场景（例如同时涉及 AI 与大数据）。此时列出多个，把最贴合、最推荐的首选场景放在最前，其余关联场景依次排后；二级场景按同样顺序与一级场景一一对应。例如：`AI`、`数据分析与管理`。

## 其他标签

只能使用 `OfficeAce`、`码道`、`AgentArts`、`免费试用`：

- 明确以某产品为主要用户入口及长期承载产品时，添加该产品标签。
- 多个产品同时出现时，只标记主要入口和长期承载产品，不全部添加。
- 仅在明确已提供免费试用能力时添加`免费试用`。
- 没有适用标签时留空，不自行生成其他标签。

## 英文名称与 ID

- 英文名与中文名含义一致，使用自然、简洁且适合官网展示的英文，不逐字硬译；保留官方产品及项目英文名称。
- ID 由英文名生成：全部小写，单词间用 `-`，删除标点，将 `&` 转为 `and`，最终只能包含 `a-z`、`0-9`、`-`。

## 输出格式

应用方案、最佳实践或不含多个实现的单条命名请求，严格输出以下七个字段，每个字段之间空一行。不要使用代码块、列表或补充说明；没有其他标签时保留冒号后空白。表格维护请求则交付工作簿及同步摘要，不套用此格式。

```text
方案名或实践名：XXX

方案名或实践名（英文）：XXX

ID编码：xxx-xxx-xxx

一级场景：XXX

二级场景：XXX

主标签：应用方案 / 最佳实践 / Skills

其他标签：XXX
```

多个场景时，`一级场景`与`二级场景`用顿号分隔，首选场景放最前，两者一一对应。例如：`一级场景：AI、数据分析与管理`，`二级场景：Agent与知识应用、智能问数与数据Agent`。

Skills 聚合页请求在七字段后追加`具体 Skills`，每个产品实现一行，格式为`Tab 名称｜Skill ID｜Skill 名称`。例如：

```text
具体 Skills：
LTS｜lts-root-cause-analysis｜LTS 根因分析
CCE｜cce-root-cause-analysis｜CCE 根因分析
RDS｜rds-root-cause-analysis｜RDS 根因分析
```
