# 最佳实践文档 workflow

在用户要求最佳实践、解决方案实践文档或按模板成稿时使用，也适用于需要指导完成一个明确场景的任务。明确场景、完整实现过程和可验证结果是成稿门槛，不是要求用户提前提供的全部资料；缺项先核验补齐，仍缺失则交付标明缺口的草稿，不宣称可上架。

## 交付基线

以 [assets/解决方案实践_最佳实践文档模板_无序号.docx](../assets/解决方案实践_最佳实践文档模板_无序号.docx) 为母版，保留其页面、页眉页脚、字体、表格和标题样式，在副本中替换内容，不覆盖母版。默认交付填充后的 `.docx`；需要协作审阅时可另附同内容的 Markdown 草稿。

保留模板的一级章节顺序：文档信息 → 场景说明 → 方案设计 → 实践步骤 → 效果验证 → 相关资源。保留适用的二级标题和表格列名，按实际内容增删数据行。资源成本、部署、卸载仅在场景需要时补入相应章节；不另套部署方案模板。删除模板的“本章目标”、填写提示、示例空行及“最低上架门槛”等编辑说明。

## Workflow

1. **判定是否合格**：用一句话写清目标用户、输入或起点、完成动作和可观察结果。无法写清时，先补资料；不要把产品介绍包装成最佳实践。
2. **建立证据表**：从官方文档、官方仓库和用户材料核验产品能力、区域、权限、版本、配额、命令、参数及链接。记录核验日期；无法验证的内容标为待确认，不编造操作结果。
3. **设计方案**：先确定组件角色、数据或调用流、选型理由、权限边界和适用限制，再画架构图。组件名和连线必须与正文步骤一致。
4. **跑通主路径**：按真实业务流程写 3–8 个主步骤。每步包含前置状态、操作、关键输入或配置、预期中间结果；不要把每次点击拆成一级标题。涉及命令或配置时给出可复制内容，并说明需替换的值。
5. **定义验收**：为每个核心结果写验证方法、预期结果和通过标准，并提供一个完整的典型输入/输出示例。操作完成不等于验证通过。
6. **填充母版**：先填文档信息，再依次完成场景说明、方案设计、实践步骤、效果验证和相关资源。删除所有 `[填写]`、`[插入…]` 和无内容示例行。
7. **交付检查**：逐项复核链接、命令、参数、图文一致性和可复现性；确认没有虚构实测、未解释权限或模糊的“成功”结论。

## 各章节写法

- **文档信息**：名称、英文名、URL ID、场景分类、标签、Owner、版本和日期必须互相一致。ID 使用英文小写和连字符，主标签为“最佳实践”；一级场景采用模板列出的分类，二级场景依用户提供的分类体系填写，不自创固定分类。无其他标签时留空，Owner 等未知信息明确写“待确认”，不要猜测。
- **场景说明**：写真实问题、适用对象和最终效果；避免行业背景与产品宣传铺垫。
- **方案设计**：架构图之后解释每个组件的职责及关键设计取舍，不重复官网功能列表。
- **实践步骤**：准备工作只列实际依赖；关键配置表只保留会改变结果的参数。
- **效果验证**：优先使用可观察、可重复的判据，例如状态、响应、日志、指标或输出文件；不要使用“运行正常”等不可审计表述。
- **相关资源**：链接到本实践直接依赖或合理承接的应用方案、Skills 和官方文档，不堆砌泛相关链接。

若内容尚未实际跑通，在交付中明确标注“文档级核验”及未验证步骤；不得写成已经实测通过。

## 模板字段与内容映射

| 模板位置 | 成稿内容与判据 |
| --- | --- |
| 场景说明 / 背景与问题 | 描述起点、实际障碍以及本实践解决的范围。 |
| 适用对象与场景 | 沿用“对象/场景、现状问题、实践目标”三列，每行描述一个真实适用对象或场景。 |
| 最终效果 | 列出可观察产物，与效果验证的验证项逐一对应。 |
| 方案设计 / 整体架构 | 图中标明组件、数据或调用方向及必要边界；正文解释主链路。Word 中插入实际图片，不留下 Mermaid 源码代替图片。 |
| 产品与组件 | 沿用“产品/组件、类型、本实践中的作用”三列，类型区分云产品、开源组件、自有系统等。 |
| 关键设计 | 解释影响结果的选型、流程、权限、数据处理及限制；无需罗列所有可能的设计点。 |
| 实践步骤 / 准备工作 | 列明账号权限、版本、依赖、样例数据和可访问入口，不填写真实密钥。 |
| 操作步骤 | 以业务主流程组织；命令注明执行位置、替换参数、预期输出，涉及数据修改时说明影响和必要恢复方法。 |
| 关键配置 | 沿用“配置项、推荐值/示例、说明”三列，示例值和已验证值应可区分。无独立配置时写明不适用并删除空表。 |
| 效果验证 | 沿用“验证项、验证方法、预期结果、通过标准”四列，判据必须可由读者重复检查。实测状态写在正文，预期结果不冒充已观察结果。 |
| 示例输入与结果 | 给出贯穿操作与验证的完整样例，注明输入方式和输出含义；未执行的输出标为预期示例。 |
| 相关资源 | 沿用“资源类型、名称、用途/下一步、链接”四列，提供直接链接；没有关联应用方案或 Skill 时不编造。 |

## Word 成稿与核验

- 在母版副本中填充内容。优先使用环境已有的 Word 编辑工具或 `python-docx`；不得用从零新建文档代替套用母版而丢失样式。
- 替换正文与表格单元格时保留原段落、字符样式和表格属性。新增行、操作段落应沿用对应样式；检查跨 run 的占位符，避免残留半截提示或损坏超链接。
- 架构图先按正文生成，再转为当前 Word 工具支持的图像格式并嵌入。图片保留清晰文字、说明和适合页面的尺寸，不引用交付目录外的临时图片。
- 默认输出 `output/<实践ID>.docx`。用户要求 Markdown 时按同一结构输出 `.md`，以相对路径引用实际图像；需要共同交付时两种正文保持一致。
- 保存后重新打开 `.docx`，检查章节顺序、表格内容、图片存在、链接和占位符清理。条件允许时渲染检查分页、表格溢出及图中文字；无法渲染时明确仅完成结构核验。
- 最终交付说明文档路径、核验级别（实测 / 文档级核验）和影响复现或上架的待确认项。工具不足以生成 Word 时交付同结构 Markdown 草稿并说明 Word 未完成，不把草稿称为完整交付。
