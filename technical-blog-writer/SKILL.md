# 技术博客写作

交付一篇值得读、技术可信、可直接发布的文章。围绕问题和决策组织内容，让产品自然出现在解决路径中，不把文档改写成功能清单。

## 先确定写作任务

从用户资料中判断文章类型、主要读者和唯一的首要目标。类型可包括科普、实践、产品或开源项目介绍、解决方案、行业场景、案例复盘、软文、深度文章和教程。缺少非关键参数时做合理假设并继续；只有会实质改变文章方向时才提问。

先形成一句核心判断，作为全文的信息增量，例如“真正的问题不是 X，而是 Y”。围绕它设计叙事，而不是套固定模板。通常可沿着以下路径展开，按任务删减或重排：

1. 用具体问题、现象或矛盾开场。
2. 解释问题为什么难，以及已有做法的限制。
3. 提出关键判断，自然引出方案。
4. 说明架构、数据流、技术选择和取舍。
5. 给出完整的使用、部署或实践流程。
6. 解释价值产生的机制、适用场景与边界。
7. 以技术判断、实践建议或下一步演进收束。

不要使用“产品是什么—功能—优势—总结”的说明书结构，也不要为了整齐让每节等长。

## 核验事实

文章涉及真实产品、项目、规格、版本、价格、架构或能力边界时，写作前检索最新资料。依次优先：官方文档、官方仓库、官方博客、论文、官方案例、高质量技术社区和第三方评测。不要把搜索摘要当作证据。

区分三类内容：

- 已验证事实可以确定陈述，并在适合发布渠道的情况下附直接来源链接。
- 基于架构或资料得出的推断必须使用“从……来看”“更适合……”等分析语气。
- 价值或营销判断必须由具体场景、机制或数据支撑，不使用“最佳”“领先”“极大提升”等无依据结论。

没有真实体验或用户数据时，不得写“我们实测”“实践证明”。资料缺失就明确未知，不补造产品能力、案例、性能数字或用户反馈。价格、版本和其他易变化信息注明核查日期。

## 规划有效配图

文章结构确定后再做视觉计划，写清每张图要解释什么。普通的 1500–2500 字文章通常使用 2–4 张图，2500–5000 字深度文章通常使用 4–7 张；以信息需要为准，不为凑数配图。

选择最省且最可信的形式：

- 架构、流程、模块关系和技术路线优先使用 Mermaid 或 SVG 等结构化技术图。
- 有真实界面时优先使用产品截图，不用生成图伪造 UI。
- 只有封面或具体业务场景适合生成位图；风格应专业、克制、现代、B2B，避免蓝紫渐变、机器人、全息屏和无意义数据流。

结构图必须与正文中的组件和数据流一致。图片紧跟它解释的段落，随后说明图中关系为什么重要。技术图使用有信息量的 caption，例如“图 2：文档从解析到检索增强回答的处理链路”，不要只写“系统架构图”。

若用户要求完整成稿和图片，实际生成所需资产并在 Markdown 中引用；不要只给图片提示词。若当前环境无法生成某类资产，优先交付可渲染的 Mermaid，并清楚标注未生成的位图。

## 写正文

多数段落保持 2–5 句，但允许重心不同。标题要表达判断或问题，避免“背景、功能介绍、产品优势、总结”等目录式标题。

术语首次出现时自然解释。重点讲清原理、架构、数据流、选择依据、trade-off、实践流程和限制。价值要写成具体因果，例如人工步骤被哪条自动化链路替代，而不是写“降本增效”。

软文以场景价值和技术可信度为主，产品能力自然露出，并保留限制。技术博客进一步强化原理与取舍，弱化产品宣传。不要把以下比例机械写进文章，但可用于校准软文重心：约 40% 问题与场景、30% 技术方案、20% 产品能力、10% 体验引导。

明确回答：

- 什么情况下值得使用？
- 什么情况下太重或不适合？
- 依赖哪些数据、基础设施或组织条件？
- 成本、复杂度和能力边界是什么？

## 独立完成 Humanization Pass

初稿完成后单独重读并改写语言节奏，而非机械替换同义词：

- 删除或改写“随着……”“在……快速发展的今天”“众所周知”“值得注意的是”“不难发现”“综上所述”“总而言之”等套话。
- 减少“首先、其次、再次、此外、同时、最后”和“不仅……而且……”式机械连接。
- 拆掉过度对称的排比与编号，保留自然长短变化。
- 用具体因果替代“强大、领先、革命性、一站式、全方位、赋能、无缝、智能化升级、降本增效”。
- 在证据允许时加入清晰的作者判断，但不虚构亲历。
- 删除不服务核心判断的信息；准确性优先于自然，可信度优先于营销。

## 交付前检查

确认开头直接进入问题，读者和目标清楚，正文有超出原始资料排列组合的信息增量，事实与判断可区分，方案边界明确。检查每张图是否帮助理解、位置与正文一致、caption 有信息量。再次搜索上述 AI 套话和营销词，逐条删除或证明其必要性。

除非用户指定路径或只要求正文，默认交付：

```text
output/
├── article.md
└── assets/
    ├── cover.png
    ├── architecture.svg
    └── workflow.svg
```

只创建文章实际需要的资产，文件名可随内容调整。在 `article.md` 中使用相对路径直接引用，例如：

```markdown
![文档从解析到回答的处理链路](./assets/workflow.svg)

*图 2：文档从解析、切分和索引进入检索增强回答的完整链路。*
```

最终稿应无需读者再拼接正文、图片或引用即可发布。
